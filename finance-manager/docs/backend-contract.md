# 后端实现与部署契约

后端仓库：[zzily/FastApi](https://github.com/zzily/FastApi)。本次在对应仓库实现了下列能力；前端通过 `GET /ledger/capabilities` 按当前账本连接启用。旧版接口返回 404 时保持兼容，不展示后端无法保存的输入。

## 发生日期与统计口径

`TransactionCreate`、`TransactionUpdate` 支持 `occurred_at: YYYY-MM-DD`，读取返回该日期及 `occurred_at_inferred`。新增省略日期时采用账本当天；更新省略时保留原值，明确传空或未来日期会被拒绝。

数据库保留创建时间，迁移将旧记录按已有账本日历日期回填，并标记为估算；用户编辑日期后取消估算标记。账单月份、筛选、排序、挂账提醒、CSV 与 `/summary?month=` 的支出聚合统一使用发生日期。

`business_loop.current_debt` 是全账本当前工作待回款存量，`period_outstanding` 是所选月份工作账单当前未关联金额；可分配收入和未结账单指标始终表示全账本当前存量。月度复盘使用期间金额，避免把期间增量当成当前余额。旧 `total_assets` 响应保留兼容，实际首页不将其显示为家庭总资产。

## 支出分类与一次支付

- `GET /expense_categories/?include_archived=true` 获取分类，`POST` 新增，`PUT /expense_categories/{id}` 重命名或停用，`DELETE` 为软停用。
- 保留 `category: work | personal`，另存 `expense_category_id`；读取提供名称，未分类记录仍可正常使用。停用分类保留历史引用，同名同类型分类不得重复。
- 月度 `chart_data.personal_category_breakdown` 返回个人消费细分类金额，首页工作垫付与个人支出仍分别计算。
- 新增个人账单时，可传 `payment_salary_log_id` 一次执行“创建消费 + 全额关联到账收入”。不足余额、工作账单或无效分类会拒绝并回滚，不产生半笔记录。仍可通过现有核销历史撤销关联。
- 账单、收入和核销金额采用 Decimal，最多两位小数；状态统一根据账单金额与已关联金额推导。

## 完整备份与恢复

`GET /ledger/backup` 返回版本 2、导出时间、校验摘要及原始账本数据：分类、账单、收入、交易、核销历史。包含备注、凭证地址和完整交易复盘，金额保留数据库精度，不受默认 100 条分页限制。前端追加当前设备的常用模板，模板不参与服务器账本摘要。

`POST /ledger/restore/preview` 校验摘要、字段、重复 ID、关联关系、余额、账单状态及数字精度，返回数量、现有数量和是否可恢复。

`POST /ledger/restore` 只允许空账本，映射新 ID 并在同一个事务恢复所有数据；失败整体回滚。摘要作为幂等标识，重复请求不新增记录。分类与目标账本已有分类按名称及类型合并，常用模板按名称重新匹配，不依赖原分类 ID。

恢复接口要求 `X-Ledger-Restore-Key`。后端通过 `LEDGER_RESTORE_TOKEN` 启用，默认关闭；密钥错误返回 401，未启用返回 403，非空账本返回 409。前端先校验并显示恢复数量，再要求用户在界面确认。更换文件或密钥后必须重新校验。

所有账本写入与快照共用账本锁，恢复在锁内重新检查空账本和幂等标识；预检之后有新数据写入时也不会覆盖。

旧版前端导出版本 1 用于查看记录及导入常用模板，不能用于完整服务器恢复。旧版列表读取已补充分页，避免超过 100 条后静默截断。

## 部署顺序

1. 先备份目标数据库并确认 `DATABASE_URL` 明确指向目标账本。
2. 在后端执行 `alembic upgrade head`，新增迁移依次为 `20261006_0004`（日期）、`0005`（分类）、`0006`（备份恢复锁与幂等记录）。所有迁移完成后再开放新版写入服务。
3. 按需要配置 `LEDGER_RESTORE_TOKEN`，部署后端；前端能力查询随后开放对应控件，再部署前端构建产物。
4. 验证旧记录、日期归属、一次支付、备份下载和空账本恢复。恢复演练应使用独立测试账本。

本次已验证隔离 SQLite 的旧数据升级、回退及再次升级，并生成 MySQL 离线迁移 SQL；未在真实 MySQL / TiDB 或线上账本执行迁移。
